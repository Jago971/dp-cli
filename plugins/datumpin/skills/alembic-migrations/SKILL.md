# Alembic migrations

## Layout

```
database/
  base.py          # DeclarativeBase, isolated so env.py can import Base alone
  models.py
  engine.py        # engine + SessionLocal, reads settings.database_url
  migrate_and_seed.py
  migrations/{env.py, script.py.mako, versions/}
alembic.ini
```

`base.py` keeps the circular import between `engine.py` and `models.py` out of `env.py`.

## `alembic.ini` and `env.py`

`alembic.ini` leaves `sqlalchemy.url =` blank, with `script_location = database/migrations` and `prepend_sys_path = .`. `env.py` supplies the URL from settings:

```python
from database.base import Base
from database import models  # noqa: F401 — registers every model on Base.metadata
from config import settings  # or `from settings import get_settings`

config.set_main_option("sqlalchemy.url", settings.database_url)
target_metadata = Base.metadata
```

Both `run_migrations_online()` and `run_migrations_offline()` pass `render_as_batch=True`. SQLite cannot `ALTER TABLE` to drop a column or change a constraint, and batch mode rebuilds the table to do it.

## Commands run in the container

Alembic lives inside the container only (see `docker-compose-conventions`), with the instance's env file (see `config-led-deployment`):

```
docker compose --env-file .env.<app>-<instance>.dev -f docker-compose.dev.yml exec <service> alembic revision --autogenerate -m "short description"
```

Use `run --rm <service> ...` when the container is down. The new file lands in `versions/`, bind-mounted back to the host.

## Review every autogenerated migration

- **Renames:** write `op.rename_table` or `op.alter_column(new_column_name=...)` plus constraint renames, even when the table is empty everywhere. Autogenerate emits drop-and-create.
- **Cross-row CHECK constraints** (an FK must point at a row sharing my parent) cannot be a DB constraint. Enforce them in application code and say why in a comment.
- **A new NOT NULL column on a table with rows** gets `add_column` plus a backfill in the same revision.

## Boot and schema lifecycle

`migrate_and_seed.py`'s `run()` calls `alembic upgrade head` first on container boot. It is idempotent, and it builds every table on an empty database. Seeding follows (see `config-led-deployment`).

Before a schema is deployed anywhere real, regenerate the initial migration in place as the design settles. Once it is live anywhere, migrate incrementally.

## Done when

- `docker compose ... exec <service> alembic check` reports no drift.
- `alembic upgrade head` succeeds on an empty DB and on a copy of the seeded DB.
- A rename revision contains `rename_table`/`alter_column` and no `drop_table`/`drop_column`.
- Every new NOT NULL column has its backfill in the same revision.
